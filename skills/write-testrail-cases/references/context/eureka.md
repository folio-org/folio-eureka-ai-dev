## What is Eureka

Eureka is the FOLIO platform architecture that replaces Okapi. API traffic goes through **Kong** (API gateway); authentication/authorization is delegated to **Keycloak** (one realm per tenant); each backend module runs behind a **sidecar** that validates the JWT and the caller's permissions. Platform-level lifecycle is handled by manager services: **mgr-tenants** (tenants ⇄ Keycloak realms), **mgr-applications** (application descriptors), **mgr-tenant-entitlements** (which applications a tenant is entitled to).

The FOLIO-facing consequences that matter for test design: legacy *permissions/permission sets* are replaced by **capabilities / capability sets / authorization roles**; a FOLIO user must be *promoted* to an **auth user** (Keycloak record) before it can log in or receive roles/capabilities; sessions are governed jointly by Keycloak realm settings (fixed-length session) and `stripes.config.js` (idle session); and in ECS every tenant is a separate Keycloak realm, which drives two different login UXs.

This is a *platform* area, not a single app: cases live under Settings > Authorization roles / Authorization policies, the Users app, Consortium manager, and login/session flows that have no app of their own.

## Key Terms

| Term | Definition |
|---|---|
| Kong | API gateway; all API calls go to `<Kong base URL>/...` with header `x-okapi-tenant`. |
| Keycloak | Identity provider. One **realm per tenant**, named after the tenant name/id. Admin console at `<Keycloak base URL>/admin/master/console`. |
| Sidecar | Per-module proxy that validates tokens and capability-based access before the request reaches the module. |
| Capability | Atomic permission unit: `<Type> - <Resource> - <Action>`, where Type ∈ Data / Settings / Procedural. |
| Capability set | Bundle of capabilities; assigning the set implicitly selects its capabilities. |
| Authorization role | Named container of capabilities/capability sets, assignable to users. Types: REGULAR / DEFAULT / CONSORTIUM. |
| Authorization policy | Keycloak policy object; a per-user policy `Policy for user: <name>` is auto-created with `source = SYSTEM` when capabilities are assigned directly to a user. |
| Auth user / Keycloak record | The Keycloak-side representation of a FOLIO user. Created by `POST /users-keycloak/users` or by promotion (`POST /users-keycloak/auth-users/{userId}`). |
| Entitlement | Link between a tenant and an application version; drives which apps/capabilities exist in that tenant. |
| Default role | Role created by an application's entitlement (e.g. "Acquisition Administrator", "Check-in All", `default-system-role-mod-circulation-bff`); `Type = Default`. |
| Central / Member tenant | ECS roles of tenants; each has its own Keycloak realm and its own entitlements. |
| Affiliation | User's membership in a tenant. The **primary** affiliation is the tenant the user was created in and the tenant they land in after login. |
| RTR | Refresh Token Rotation — stripes-core rotates `folioAccessToken` / `folioRefreshToken` via `POST /authn/refresh`. |
| FLS | Fixed-Length Session — hard session cap coming from Keycloak realm session settings. |

## Architecture / Record Hierarchy

```
Keycloak (per-tenant realm)                 Kong (gateway)  ->  sidecar  ->  module
  realm = <tenant name>                       header: x-okapi-tenant: <tenant>
  ├─ clients: <tenant>-application (login theme, SSO), password-reset-client
  ├─ realm roles  = FOLIO authorization roles (incl. default/system roles)
  ├─ realm settings > Sessions = fixed-length session limits
  └─ users        = auth users (a subset of FOLIO users)

Tenant (mgr-tenants)
  ├─ secure: true|false   (immutable after creation)
  ├─ entitlements (mgr-tenant-entitlements) -> applications (mgr-applications)
  │     └─ each entitled application supplies capabilities, capability sets, default roles, system users
  └─ users (mod-users / mod-users-keycloak)
        ├─ user record: type = staff | patron | shadow | system; username (required for staff)
        ├─ auth user (Keycloak record)  <- required for login / roles / capabilities
        ├─ credentials (mod-login-keycloak)
        ├─ authorization roles  -> capability sets -> capabilities
        └─ per-user policy "Policy for user: <name>" (source = SYSTEM)

ECS: Central tenant + N member tenants, each a full stack of the above.
     Shared (CONSORTIUM) roles are pushed from Central to members via Consortium manager.
```

## Login — non-ECS

Flow (single tenant, Keycloak-hosted login):

1. Open the environment URL → login screen with **Username**, **Password** fields and **Log in** button. If `okapi.authnUrl` is configured and `config.tenantOptions` holds exactly one entry, stripes-core redirects straight to that realm's OIDC endpoint: `<authnUrl>/realms/<tenant>/protocol/openid-connect/auth?client_id=<clientId>&response_type=code&redirect_uri=<uri>&scope=openid` [from source].
2. Submitting credentials → `GET /authn/token?code=...`. Response body contains **only** `accessTokenExpiration` and `refreshTokenExpiration`; the tokens themselves arrive as cookies **`folioAccessToken`** and **`folioRefreshToken`**. The access token must never appear in the response body [confirmed C423957].
3. `GET /users-keycloak/_self?expandPermissions=true` returns 200 with a `permissions` array derived from the user's capabilities — whether they were assigned directly or through a role [confirmed C589233]. Permissions belonging to an **unentitled** application are not returned [C1322895].
4. FOLIO welcome page; top navigation bar shows only apps the user has capabilities for; the user's first and last name appear in the profile area, top right.
5. Deep links survive login: opening `<env>/inventory` unauthenticated → login → the Inventory main page opens. After a *manual* logout the next login lands on the welcome page, not the previous app [C451519].

Constraints / notes:
- **A Keycloak record and credentials are prerequisites.** A FOLIO user created with `POST /users` alone cannot log in until it is promoted (`POST /users-keycloak/auth-users/{userId}`) or given credentials (`POST /authn/credentials`, which creates the Keycloak record when a username is present) [C451626, C451631].
- If **Kong is unavailable** or `*/authn/token?code=*` is blocked, login ends on a page with header "Logging out" and a "Log out" button — not on an app page [C630447].
- SSO: when the tenant's `<tenant>-application` client uses a Keycloak theme whose name contains `sso-only`, the native login form is suppressed — only the SSO button(s) are shown, and username/password fields plus the "Sign in with" / "Or sign in with" text are absent [C543873].
- Legacy permission UI is gone: no "User permissions" accordion on the user record, no "Permission sets" under Settings > Users, no "I can haz endpoint" / "Permissions inspector" under Settings > Developer [C442842, C633353].

## Login — ECS

In ECS every tenant is its own realm, so authentication must be pointed at a realm. Two UXs exist; which one appears is a **configuration** choice in `stripes.config.js` (`config.tenantOptions`), not a user choice [from source `AuthnLogin.js`].

### The two ECS login forms

| | **Single-UX login** (one login form) | **Tenant-dropdown login** (pre-login tenant selection) |
|---|---|---|
| Config | `config.tenantOptions` undefined or exactly **1** entry (the central tenant); falls back to `okapi.tenant` / `okapi.clientId` | `config.tenantOptions` holds **more than one** entry (central + members), each with its own `name`, `displayName`, `clientId` |
| First screen | Login form immediately (browser is redirected to the single realm's OIDC auth URL) | **Tenant/library selection screen**: `OrganizationLogo`, a **"Tenant/Library"** select whose default option reads **"Select your tenant/library"**, and a **"Continue"** button that stays **disabled** until a tenant is chosen |
| Realm used to authenticate | Always the central tenant realm | The realm of the tenant picked in the dropdown |
| Auth URL | `.../realms/<central>/protocol/openid-connect/auth?...&scope=openid` | `.../realms/<selected tenant>/protocol/openid-connect/auth?...&scope=openid&isConsortium=true` |
| Where the user lands | Their **primary affiliation** tenant, regardless of where they typed credentials — a user created in a member tenant logs in through the central URL and lands in the member tenant [C1030032 steps 6-11, C1292039 step 5] | The tenant selected on the first screen; the active affiliation after login equals that tenant [C740245 step 5] |
| Extra UI on the login form | none | **"Return to tenant/library selection screen"** link below the "Log in" button [from cases C740245] |
| Deep-linking | `<env>/inventory` → login → Inventory [C451520] | The login URL *with the tenant preselected* can be copied and reopened (including in Incognito) and still shows the selected tenant's login form [C740245] |
| Tenant options list | n/a | Sorted by `sortableName` → `displayName` → `name`; labels show `displayName` when present |
| Typical use | consortium with a single shared entry point / "one FOLIO login for everyone" | consortium where each library authenticates against its own realm |

> `SelectAndDispatchTenant` is a related component that renders a "Select your tenant/library" **select inside** the native (non-Keycloak) login form when `tenantOptions` has more than one entry, and renders `null` for central-tenant-only authn [from source]. It is not referenced from `Login.js` on `main` — see Known Gaps before writing a case against it.

Other ECS login/logout behavior:
- Affiliation switching is done from the user profile section in the top-right: **"Switch active affiliation"** → **"Select affiliation"** modal with a **"Consortium members"** dropdown → **"Save & close"**. The selected tenant name is then shown in the profile section [C423958, C449377].
- Switching affiliation triggers `GET /entitlements/{tenantId}/applications` with `x-okapi-tenant` = that tenant, so the app list in the top bar is per-tenant [C449377].
- A user whose only affiliation is a member tenant logs in and lands in that member tenant; logging out returns them to the login screen [C430269].
- Re-login destination depends on **how** the session ended: after a *session timeout* the user returns to the exact record/page and tenant they were on; after a *manual logout* they land on the FOLIO welcome page at the initial URL in their primary tenant [C1292039].
- Session timeouts are per-tenant realm settings, so Central and Member can expire at different times; the counter keeps running across an affiliation switch and is not restarted by it [C1292039 steps 10-11, C1453684, C1453689].

## Session management (RTR, idle session, fixed-length session)

Two independent timers:

| | Idle session | Fixed-length session (FLS) |
|---|---|---|
| Source of truth | `stripes.config.js` → `config.rtr.idleSessionTTL`, `config.rtr.idleModalTTL`, `config.rtr.activityEvents` | Keycloak: realm → **Realm settings > Sessions** → "SSO Session Idle", "SSO Session Max", "Client Session Idle", "Client Session Max" (set all four to the same value to define it) |
| Warning UI | **Modal** — title "Your session will expire soon!", text "Time remaining: MM:SS", **"Keep working"** button | **Message banner** below the top navigation bar — "Your session will end soon! Time remaining: MM:SS" |
| Warning lead time | `idleModalTTL` before expiry | `config.rtr.fixedLengthSessionWarningTTL` — **1 minute** in practice |
| Dismissing the warning | "Keep working" **or** ESC resets the idle timer; the countdown reaching zero after dismissal does nothing | Cannot be dismissed or extended — expiry is a hard cap |
| On expiry | `POST /authn/logout` (204) → screen with "Your session expired due to inactivity." + **"Log in again"** link | Redirect to the logout page with a **"Log in again"** button |
| After re-login | The page open before expiry is restored (unsaved form input is cleared) | Same — the page is restored, form fields are back to defaults |

Additional confirmed behavior:
- Token rotation: while the user works, `POST /authn/refresh` returns 201 and both cookie expirations move forward. Rotation keeps working in a second tab after the tab used to log in is closed [C514952].
- FLS timers are **per session**, not per user: two browsers logged in as the same user expire independently, each restoring its own page after re-login [C506678].
- The FLS countdown reflects *actual* remaining session time — it must not restart on page reload, on opening the same page in a second tab, or on switching affiliation [C1453684, C1453685, C1453689, C1453712].
- Tabs are synchronized through a BroadcastChannel: activity in one window pings the idle timers of the others [from source `SessionEventContainer.js`].
- Logout: user profile menu → "Log out" → logout screen with "You have logged out." + "Log in again". With `confirmLogout = false` (default) there is no confirmation step [C436889].

## Password management — constraints

- **Username is mandatory for authentication.** Any attempt to create a Keycloak record, credentials, or a role/capability assignment for a user without a username fails with `"User without username cannot be created in Keycloak"` (400 via `POST /users-keycloak/auth-users/{id}`, 500 via `POST /authn/credentials` and `POST /authn/update`) [C451626, C451631, C594518, C627403]. `patron`-type users do not require a username — the field's required marker disappears when User type is switched to patron [C1051455].
- Credentials APIs: create `POST /authn/credentials` (201, creates the Keycloak record when a username is present); change `POST /authn/update` with `password` + `newPassword` (204); unknown username → 404 `"Failed to find user by name: username = <...>"` [C451626, C594518].
- Assignments require a Keycloak record: `POST /roles/users`, `POST /users/capabilities`, `POST /users/capability-sets` return **404 "Keycloak user doesn't exist"** for non-auth users [C627444, C627445].
- **Reset-password link**: Users app → user → Actions > Edit → **"Send reset password email"** link next to the Username field → "Reset password email sent" modal shows the URL, matching the `link` property in the `POST /users-keycloak/password-reset/link` response. Requires `Procedural - UI-Users Reset Password - Execute` **and** `Procedural - Users-keycloak Password-Reset-Link Generate - Execute` [C434077].
- The link's base URL is configurable at runtime: `PUT <Kong>/base-url` with `{"baseUrl": "..."}` changes the host used in generated links [C1322906]. UI path default `/reset-password` [from source].
- Link lifetime: `RESET_PASSWORD_LINK_EXPIRATION_TIME` = **24 hours** (`KC_PASSWORD_RESET_TOKEN_TTL` = 86400 s, max 4 weeks) and the link is **single-use** — reuse or expiry shows "Your choose password link expired or has already been used…" [from source].
- Password rules enforced on the "Choose a password" page [from source `stripes-core/en.json`]: minimum 8 characters; both lower- and uppercase letters; ≥1 digit; ≥1 special character; must not contain the username; no keyboard sequence; no repeated character in a row; no whitespace (and no consecutive whitespace); not commonly-used/compromised; not one of the last ten passwords.
- Account lockout and disabled accounts are Keycloak-side: an **inactive** user entering the correct password sees `"Account is disabled. Contact your administrator"` above the Username field (Umbrellaleaf onward; earlier releases showed "Invalid username or password.") [C1030031, C1030032 — KEYCLOAK-101]. Brute-force strings "You have entered the wrong username or password for the third time…" / "For security purposes, your account has been locked…" exist in stripes-core but are not covered by any case [from source].
- Migration/system-user specifics: `DEFAULT_PASSWORDS_ON_MIGRATION=false` (migrated users get no credentials unless enabled); generated system-user passwords are 32 chars [from source].

## Tenants, Keycloak records, authorization roles

**Tenants**
- Creating a tenant creates the matching **Keycloak realm**; every tenant-scoped operation happens inside that realm [from source `mgr-tenants`].
- `POST <Kong>/tenants` accepts an optional boolean **`secure`**. Omitted → the field is absent from the response; `true`/`false` → stored and returned; a non-boolean (`"no"`) → 400. `secure` is **immutable**: any `PUT` that adds or changes it returns 400 `"Secure field cannot be modified"`. Tenants can be filtered with `GET /tenants?query=secure=true|false` [C503152, C503153].
- A tenant **cannot be deleted while applications are entitled** to it: `DELETE /tenants/{id}` → 400 "tenant cannot be removed because it has installed applications"; after `DELETE /entitlements` it returns 204 [C895662].
- Backend admin auth for platform endpoints is a client-credentials token from `POST <Keycloak>/realms/master/protocol/openid-connect/token`; tenant-scoped API auth is `POST /authn/login-with-expiry` with `x-okapi-tenant` [corpus-wide pattern].

**Keycloak records (auth users)**
- `GET /users-keycloak/auth-users/{userId}` → **204** when the user has a Keycloak record, **404 "Not Found"** when not. `POST /users-keycloak/auth-users/{userId}` promotes: 201 for a first promotion, 204 when already promoted, 404 for a random UUID, 400 when the user has no username [C451631, C451632].
- The UI creates records on demand and always asks first:
  - Settings > Authorization roles → role → "Assign/Unassign" → Save → **"Create user records in Keycloak"** modal: "This operation will create new records in Keycloak for the following users: <UUIDs>", Cancel / Confirm. Cancel or ESC assigns **nobody** — users without records are dropped and only the already-promoted user stays assigned; Confirm sends one `POST /users-keycloak/auth-users/{id}` per user (201) and all rows appear [C627395, C627404].
  - Users app → user → Edit → assign a role → Save & close → **"Keycloak user record"** modal: "This operation will create new record in Keycloak for <last name, first name middle name> in the <tenant> tenant." Cancel leaves the role count unchanged [C1347148-C1347151].
- Duplicate emails: with Keycloak's "Duplicate emails" toggle off, promoting a second user with an existing email fails with "Failed to create user records in keycloak for users: <id>: Failed to create keycloak user: userId = <id>, realm = <tenant>"; enabling the toggle makes the same assignment succeed with "Keycloak records created for the following users: <id>" [C889748].
- Deleting a user (`DELETE /users-keycloak/users/{id}`, 204) cascades: user policies, user roles, user capabilities and user capability sets all return empty collections afterwards [C436914].

**Authorization roles**
- Role list columns: **Name, Description, Type, Updated, Updated by**. Detail view has "Capabilities" and "Capability sets" accordions with counters, an "Assigned users" accordion, "General Information", and (in ECS/Consortium manager) a "Centrally managed" value [C502978, C446120].
- Role types: **REGULAR** (created by users), **DEFAULT** (created by application entitlement, incl. `default-system-role-*` for system users), **CONSORTIUM** (result of sharing). The UI renders them as `Type = Regular / Default / Consortium`.
- **Default roles are read-only**: the Actions menu offers only "Duplicate" (no Edit/Delete), the direct `/edit` URL renders a blank page, and the API rejects both directions of a type change with 400 `"Default role cannot be created, updated or deleted via roles API."` [C794509, C957370].
- Default roles come and go with entitlements: entitling `app-platform-minimal` creates them in the Keycloak realm; `DELETE /entitlements?purge=true` removes them, restoring the pre-entitlement realm role list [C494090]. Each application's system users get their own default role with the module's capabilities [C784506].
- Duplicating a role copies capabilities and capability sets but **never** the assigned users; the new pane is titled `<role name> (duplicate) <n>` [C554636].
- Deleting a role with capabilities and users assigned is allowed after confirming the "Delete role" modal; Cancel keeps the record [C446119, C446120].
- Capability API details: `GET /roles/{id}/capabilities` marks directly-assigned capabilities `"direct": true` and set-derived ones `"direct": false` (with `expand=true`); `dedup=false` returns an overlapping capability twice (direct + indirect), the default dedups to the `direct` entry, and an invalid `dedup` value returns 400 [C1375886].
- Capability-set semantics in the UI: checking a capability set auto-checks its capabilities, and unchecking it releases them [C434129, C503019, C1395070, C1395071].

**Authorization policies**
- Assigning capabilities directly to a user auto-creates `Policy for user: <name>` with `source = SYSTEM`; a `PUT` that tries to change `source` to `USER` returns 204 but the value stays **SYSTEM** [C514999]. `source` is not user-editable [C514991].

- **Role Type**: Regular (REGULAR), Default (DEFAULT), Consortium (CONSORTIUM)
- **Centrally managed** (ECS role detail): Yes / No

- **Policy source**: SYSTEM, USER (USER not settable for auto-created user policies)

- **Tenant `secure`**: true / false / absent
- **Auth-user check** `GET /users-keycloak/auth-users/{id}`: 204 = record exists, 404 = no record

## Capability Sets (Eureka)

> Format: `<Type> - <Module/Resource> - <Action>`. These are the sets actually used in this section's preconditions (frequency in the 207-case corpus).

## Common Verification Patterns

### Login + token verification

```
Action:   Press "F12" to open browser DevTools > select "Network" tab, then log in as the user from Preconditions #N
Expected: FOLIO welcome page is shown with the top navigation bar including available apps
          In DevTools:
          - GET /users-keycloak/_self returns 200 with "expandPermissions=true"; "permissions" includes "<permission name>"
          - Response of GET /authn/token contains only "accessTokenExpiration" and "refreshTokenExpiration"
          - Cookies "folioAccessToken" and "folioRefreshToken" are set
```

### Fixed-length session expiry (Keycloak-driven)

```
Precondition: In the Keycloak admin interface, for the <tenant> realm, "Realm settings" > "Sessions" is saved with
              "SSO Session Idle" / "SSO Session Max" / "Client Session Idle" / "Client Session Max" = 2 minutes
Action:   Wait until the fixed-length session warning appears (1 minute before session expiry)
Expected: Banner below the top navigation bar: "Your session will end soon! Time remaining: 01:00"; the value decreases by one second every second
Action:   Wait until the counter reaches "00:00"
Expected: User is redirected to the logout page with "Log in again" button
Last step: In the Keycloak admin interface, restore the initial session parameters for the <tenant> realm, as they were before Preconditions
```

### Promoting a user / assigning a role that needs a Keycloak record

```
Action:   Select the user without a Keycloak record in the "Select User" modal and click "Save"
Expected: "Select User" modal is closed; "Create user records in Keycloak" modal is shown with:
          - Text: "This operation will create new records in Keycloak for the following users: <user UUIDs>"
          - "Cancel" button
          - "Confirm" button
Action:   Click "Cancel" button
Expected: Modal is closed; "Assigned users" accordion does NOT include the user; already-promoted users remain assigned
Action:   Repeat the assignment and click "Confirm" (DevTools open)
Expected: "Assigned users" accordion includes the user; POST /users-keycloak/auth-users/<user UUID> returns 201
```

Action:   Go to "Settings" app > "Authorization roles"

## ECS / Multi-Tenant Notes

- 78 of 207 cases are ECS (`ECS Enabled = true`), concentrated in Login > Consortia (32029), Users > Consortia (42028) and Consortium manager (Eureka) (40125). `Multi-Tenant` is `false` on **every** case in this subtree — ECS coverage is flagged with `ECS Enabled`, not `Multi-Tenant`.
- Preconditions in ECS cases always state: which tenant each user was created in, the user's affiliations, and the capability sets **per tenant** (they routinely differ — e.g. Consortium-manager and Affiliations sets exist only in Central).
- Only roles that live in the **Central** tenant can be shared: for a role created in a member tenant the "Share to all" option is absent from the Actions menu [C523604].
- Role-name uniqueness for sharing/renaming is **case-insensitive across all member tenants**; the error toast names the offending members. Sharing succeeds only after the clashing names are made unique [C692096, C1030054, C1263896].
- A shared role in a member tenant carries the same capabilities/sets but has **no assigned users** there; members' own like-named local roles keep their own users and capabilities untouched [C692096].
- Sharing with only Central selected in "Select members" still converts the role to CONSORTIUM; in member tenants the role is then visible but has no "Actions" button for users lacking member-tenant capabilities [C523612].
- The "User roles" accordion shows an **"Affiliation" dropdown only for `staff` users** (defaulting to the primary affiliation); it disappears for `patron` users, and switching type shows the "Changing user type?" confirmation modal [C1051455].
- Assigning a role in Central vs Member decides which realm gets the Keycloak record; the "Keycloak user record" modal names the tenant, and assignment order (Central-then-Member vs Member-then-Central) is an explicit test dimension [C1347148-C1347151].
- Compare-users / compare-capabilities views in Consortium manager query `/users` with `limit=4000` and include only `staff`, `shadow` and `system` users — `patron` users are excluded [C1009047].

## Key Business Rules for Test Cases

1. A FOLIO user cannot log in, hold roles, or hold capabilities without a Keycloak record (auth user); promotion is required first (cases + github).
2. A user without a username can never be given a Keycloak record — every such attempt fails with "User without username cannot be created in Keycloak" (cases).
3. `POST /authn/credentials` with a username creates both credentials and the Keycloak record; the user can then log in immediately (cases).
4. Role/capability assignment APIs return 404 "Keycloak user doesn't exist" for non-auth users; the UI instead offers to create the records and assigns nobody if the confirmation is cancelled (cases).
5. Login response never exposes the access token in the body — tokens are delivered as `folioAccessToken` / `folioRefreshToken` cookies (cases).
6. `GET /users-keycloak/_self?expandPermissions=true` returns the permissions of directly-assigned **and** role-derived capabilities, and drops permissions of unentitled applications (cases).
7. Deep-linked URLs are restored after login; after a manual logout the user lands on the welcome page instead (cases).
8. The idle session warning can be dismissed ("Keep working" or ESC) and resets the timer; the fixed-length session warning cannot be dismissed and always ends in logout (cases).
9. The fixed-length session countdown shows real remaining time — it survives page reload, a new tab, and an affiliation switch without restarting (cases).
10. Fixed-length sessions are per session/browser, not per user (cases).
11. After a session-timeout logout the user returns to the same page **and tenant**; after a manual logout to the welcome page in their primary affiliation (cases).
12. In ECS the landing tenant is the user's primary affiliation when a single login form is used, and the selected tenant when the tenant-dropdown login is used (cases + github).
13. The ECS tenant-selection screen keeps "Continue" disabled until a tenant is picked, and its URL can be reused with the tenant preselected (cases + github).
14. With an `sso-only` Keycloak theme, native username/password login is unavailable for that tenant (cases).
15. Password reset links are generated per user, expire after 24 hours, are single-use, and their base URL is configurable through `PUT /base-url` (cases + github).
16. Legacy permission UI (User permissions accordion, Permission sets, Permissions inspector) is absent on Eureka (cases).
17. Default roles cannot be created, edited or deleted — in the UI (only "Duplicate" offered, `/edit` URL blank) or via the API (400) (cases).
18. Default roles are created and purged with application entitlements; each application's system users get a default role carrying that module's capabilities (cases).
19. Duplicating a role copies capabilities and capability sets but never assigned users (cases).
20. Deleting a user removes its policies, roles, capabilities and capability sets (cases).
21. Assigning capabilities directly to a user creates a `Policy for user: <name>` policy with `source = SYSTEM`, and the source cannot be changed to USER (cases).
22. A tenant's `secure` flag is set only at creation and can never be modified (cases).
23. A tenant cannot be deleted while it has entitled applications (cases).
24. Only Central-tenant roles can be shared; sharing sets Type = Consortium and "Centrally managed" = Yes (cases).
25. Sharing or renaming a role fails when the name already exists (case-insensitively) in any member tenant, and the error names those members (cases).
26. A shared role in a member tenant has the member's own users unassigned — sharing never carries user assignments (cases).
27. The "Affiliation" dropdown in "User roles" exists only for staff users (cases).
28. `patron` users are excluded from user/capability comparison views, which request `/users` with `limit=4000` (cases).
29. Capability sets and their capabilities are selected/deselected together in the role editor (cases).
30. `GET /roles/{id}/capabilities` dedups direct and set-derived duplicates by default; `dedup=false` returns both entries and an invalid value returns 400 (cases).
