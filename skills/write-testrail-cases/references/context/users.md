## What is Users

The Users app is the central record for both patrons and library staff in FOLIO. It supports searching, creating, editing, and governing user profiles used by circulation, requests, fees/fines, blocks, and access control. Staff users differ from patrons by having login identity and assigned authorization roles/capabilities.

---

## Key Terms

| Term | Definition |
|---|---|
| User record | Core profile for a person in FOLIO (patron or staff) |
| Patron group | Classification driving policy behavior (loans, fees/fines thresholds, expiration defaults) |
| User role | Eureka authorization role containing capabilities/capability sets |
| Patron block | Restriction that can block borrowing, renewals, and/or requests |
| Proxy/sponsor | Relationship allowing a proxy to act on behalf of a sponsor |
| Actual cost | Lost-item fee flow where staff manually apply or skip billing |

## Lifecycle / Workflow

User status:

Active -> Inactive (expiration date passes or staff sets inactive)
Inactive -> Active (staff reactivates)

Proxy relationship:

Active -> Inactive (expiration or manual change)

Loan claim flow from Users:

Open loan -> Claimed returned -> (Found/check in) Closed
Open loan -> Claimed returned -> Missing
Open loan -> Declared lost (lost fee flow)

| Status | Description |
|---|---|
| Active | User can perform normal circulation actions |
| Inactive | User cannot log in/check out/renew/place requests |
| Claimed returned | Loan remains open, overdue accrual paused |
| Declared lost | Lost-item policy and billing logic applied |

## Key Business Rules for Test Cases

1. Last name, patron group, status, email, and preferred contact are required to save a user record. (cases + source)
2. Selecting a patron group defaults status to Active; status can be manually changed. (cases + source)
3. Expiration date is optional; once passed, user becomes Inactive by scheduled process. (cases + source)
4. Inactive users cannot log in, check out, renew, or place requests. (source)
5. Password is not set directly in profile edit; reset password link workflow is required. (source)
6. User type is required in ECS and reading-room-access flows; staff uses username/login, patrons generally do not. (source)
7. Proxy/sponsor relationships are managed in user record and include active/inactive relationship status plus optional expiration. (source)
8. Manual patron blocks can restrict borrowing, renewals, and requests; blocks with expiration auto-expire. (source)
9. A user cannot be deleted while open loans/fees-fines/requests exist; open transactions must be cleared first. (cases + source)
10. Claim returned keeps loan open and pauses overdue fine progression until resolved. (source)
11. Declared lost invokes lost-item fee policy behavior and follow-up billing flow. (source)
12. Actual-cost lost items require explicit staff decision to bill or do not bill. (source)
13. In Eureka, user access is role/capability based, replacing legacy permission-set model. (source)
14. Profile picture management requires both tenant configuration and profile-picture capabilities. (cases + source)
