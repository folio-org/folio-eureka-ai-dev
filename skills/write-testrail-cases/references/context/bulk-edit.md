## What is Bulk Edit

Bulk Edit is a FOLIO app for applying the same change to many records in one job. It supports Inventory and Users, with identification by uploaded identifiers or by in-app query. The app includes matching preview, controlled commit, post-commit downloads, and auditable logs.

---

## Key Terms

| Term | Definition |
|---|---|
| Identifier flow | Upload a one-column CSV of record identifiers and match records before editing. |
| Query flow | Build and test a query in-app, then run matching and bulk edit from that result set. |
| Preview of records matched | Accordion containing matched records and columns selected under Actions > Show columns. |
| Errors and warnings | Accordion showing failed identifier matches or per-record warnings during/after commit. |
| Bulk edit profile | Reusable profile (Settings) for options/actions, including FOLIO and MARC instance variants. |
| Commit changes | Irreversible apply step after confirmation preview. |

## Lifecycle / Workflow

Identifier/query to commit flow:

1. Select record type and identifier (or build query).
2. Upload/test and retrieve matching records.
3. Open Start bulk edit.
4. Configure one or more bulk edit rows.
5. Confirm changes and review preview.
6. Commit changes.
7. Review changed records and warnings.
8. Download matched/changed/errors CSV files as needed.

Log-oriented statuses used in this area:

| Status | Description |
|---|---|
| Started | Bulk edit job started and visible in logs. |
| Ended | Bulk edit job finished and visible in logs. |
| Completed | Job finished without blocking failure. |
| Completed with errors | Job finished, but some records produced errors/warnings. |
| Failed | Job execution failed before successful completion. |

## Key Business Rules for Test Cases

1. A bulk edit job can process up to 100,000 records; larger result sets must be narrowed before execution. (cases + source)
2. Identifier upload requires exactly one CSV column; malformed files are rejected immediately. (cases + source)
3. Query flow requires explicit Test query before running and committing changes. (cases + source)
4. Build query capability is separate from edit capabilities. (cases)
5. In-app users editing and local CSV users editing are separate capability boundaries and workflows. (cases + source)
6. Preview before commit is mandatory; commit cannot proceed until preview is ready. (cases)
7. Are you sure? preview is a checkpoint with Keep editing, Download preview, and Commit changes actions. (cases + source)
8. Commit changes is irreversible in-app; rollback requires a new corrective bulk edit job. (source)
9. Multiple fields can be changed in one job by adding rows in Bulk edits. (cases + source)
10. Clear field removes value (null/empty behavior), not a text replacement. (source)
11. Add note appends and does not replace existing notes. (source)
12. Matching errors do not block updates on successfully matched records. (cases + source)
13. Errors and warnings are downloadable independently from changed records. (cases + source)
14. Item status and some inventory transitions remain constrained by inventory/circulation rules. (source)
15. Query and logs tabs are capability-gated; users without required capabilities cannot execute those flows. (cases)
16. MARC-protected fields are not editable via Bulk Edit (for example control fields and protected 999 ff behavior). (source)
17. Logs are durable audit history and include method, actor, processing counts, and completion status. (cases)
18. Bulk edit profiles in Settings control reusable options/actions and include lock/delete management paths. (cases)
