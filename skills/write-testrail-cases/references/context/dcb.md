## What is DCB

DCB (Direct Consortia Borrowing) is a cross-ILS circulation integration that allows consortium member libraries to borrow and lend physical items across different Library Services Platforms. FOLIO participates in DCB transactions in three distinct roles: **Lending library** (item owner), **Borrowing library** (patron's home library), and **Pickup library** (where patron collects the item). DCB itself acts as an orchestrator/broker, coordinating state transitions between all involved systems via a polling mechanism.

The FOLIO-side implementation consists of three modules: `edge-dcb` (REST API gateway + API key auth), `mod-dcb` (transaction state machine + coordination), and `mod-circulation-item` (virtual item/patron abstraction). Virtual items and virtual patrons are created automatically in lending and pickup libraries; the patron in the borrowing library is always a real existing user.

DCB Admin for Libraries is a separate web application (by Knowledge Integration) for library staff to place and monitor DCB requests, distinct from the consortia-level DCB Admin tool.

## Testing Environment Limitations

Currently there are no available instances of DCB hub or DCB Admin to connect to and test the whole end-to-end flow or observe how it works from multiple libraries' perspectives. Only a single library point of view is available at a time — either a Lender, a Borrower, a Borrowing-Pickup, or a Pickup library. Actions that need to be performed on the other side of a transaction are simulated by API calls to the `/status` endpoint or other endpoints (e.g. for renewal).

There are some test cases describing an "e2e" flow involving several connected libraries, but all of them are **not fully testable** due to the unavailability of full integration via DCB hub / DCB Admin.

`holdCount` is available only for **Lender** transactions in the GET transaction status response.

## Key Terms

| Term | Definition |
|---|---|
| DCB | Direct Consortia Borrowing — the orchestrator system connecting ILS platforms |
| Transaction | A single lifecycle unit representing one cross-institutional borrowing event |
| Virtual patron | A synthetic user record created in lending/pickup libraries to represent the borrowing patron |
| Virtual item | A synthetic item record created in borrowing/pickup libraries to represent the lent item |
| Lending library (Owning library) | The library that owns the physical item; creates a Page request for a real item |
| Borrowing library | The patron's home library; the patron is a real existing user; receives a Hold request for a virtual item |
| Pickup library | The library where the patron picks up the item; may be same as borrowing or different |
| BORROWING-PICKUP | Combined role: a single library acts as both Borrowing and Pickup |
| Self-borrowing | A transaction where the patron picks up at their own (borrowing) library using `selfBorrowing: true` |
| DCB SP | Automatically created service point (format: `DCB_{libraryName}_{servicePointName}`) used for automatic check-in/check-out events. Note: the base service point used in DCB actions is simply named `DCB` — "DCB SP" is not an entity name. |
| DCB Calendar | A common calendar automatically assigned to all DCB-created service points |
| Shadow location | A virtual location created by DCB for routing items |
| OpenRS | Open Resource Sharing — the OLF project umbrella; DCB is its cross-ILS borrowing component |
| LOCATE DCB | The OPAC built on top of OpenRS/DCB for patron-facing discovery |
| Agency | The institutional unit participating in resource sharing (synonymous with library in most contexts) |
| HostLMS | DCB's abstraction for a library management system instance |

## Record Hierarchy / Architecture

```
DCB Transaction (mod-dcb)
  |-- Role: LENDER / BORROWER / PICKUP / BORROWING-PICKUP
  |-- Status: CREATED → OPEN → AWAITING_PICKUP → ITEM_CHECKED_OUT → ITEM_CHECKED_IN → CLOSED
  |
  |-- CirculationItem (mod-circulation-item) [virtual item in Borrowing/Pickup library]
  |     |-- id, barcode, title, materialType, locationCode
  |     |-- lendingLibraryCode
  |
  |-- Virtual Patron (mod-users, type=dcb) [in Lending/Pickup library]
  |     |-- patronGroup, barcode, localNames → firstName, middleName, lastName
  |     |-- default lastName: "DcbSystem" (if localNames not provided)
  |
  |-- Service Point (created or reused per pickup object in payload)
  |-- FOLIO Request (mod-circulation)
  |     |-- Lending: Page request, real item, virtual patron
  |     |-- Borrowing/Pickup: Hold request, virtual item, real/virtual patron
  |
  |-- FOLIO Loan (created automatically on ITEM_CHECKED_OUT transition)
```

## Lifecycle / Workflow

### Transaction Status Transitions

| From Status | To Status | Trigger |
|---|---|---|
| — | CREATED | POST `/transactions/{id}` (DCB creates transaction) |
| CREATED | OPEN | Manual check-in at Lending library (item goes In Transit) |
| OPEN | AWAITING_PICKUP | Automatic check-in at pickup SP (item goes Awaiting pickup) via PUT status |
| AWAITING_PICKUP | ITEM_CHECKED_OUT | Manual check-out at Pickup/Borrowing library |
| ITEM_CHECKED_OUT | ITEM_CHECKED_IN | Patron returns item; manual check-in at Borrowing/Pickup library |
| ITEM_CHECKED_IN | CLOSED | Manual check-in at Lending library (final return) |
| Any (before ITEM_CHECKED_OUT) | CANCELLED | FOLIO user cancels request OR DCB initiates cancellation |

### FOLIO Item Status During Lending Flow

| DCB Transaction Status | FOLIO Item Status |
|---|---|
| CREATED | Paged (if item was Available) or Hold (if checked out) |
| OPEN | In Transit |
| AWAITING_PICKUP | Awaiting pickup |
| ITEM_CHECKED_OUT | Checked out |
| ITEM_CHECKED_IN | In Transit (back to lending library) |
| CLOSED | Available |

### FOLIO Request Status During Flow

| Stage | Request Status |
|---|---|
| Transaction created | Open - Not yet filled |
| First check-in at Lending | Open - In transit |
| Item arrives at Pickup SP | Open - Awaiting pickup |
| Item checked out | Closed - Filled |

### Workflow Types (from Workflow Determination Rules)

| Workflow Code | Lending | Borrowing | Pickup | Supported |
|---|---|---|---|---|
| RET-STD | Library A | Library B | Library B | Yes |
| RET-LOCAL | Library A | Library A | Library A | Yes |
| RET-PUA (Pickup Anywhere) | Library A | Library B | Library C | Yes |
| RET-EXP (Expedited/On-site) | Library A | Library B | Library A | Yes |

- `Users > filter by User type = DCB` — find DCB virtual users
- `Circulation log > filter by service point = DCB` — view DCB system events
- `Settings > Calendar` — manage DCB calendar assignment to service points

## Transaction API Payloads

### Create Transaction — LENDER role (POST)

```json
{
  "item": { "id": "<item UUID>", "barcode": "<barcode>" },
  "patron": { "id": "<virtual patron UUID>", "group": "staff", "barcode": "<barcode>", "localNames": ["<FirstName>", "<LastName>"] },
  "pickup": { "servicePointId": "<SP UUID>", "servicePointName": "<name>", "libraryCode": "<5-char code>" },
  "role": "LENDER"
}
```
- `servicePointId` is optional for Lender
- If `localNames` not provided, default lastName = `DcbSystem`
- Item must be in Available status (creates Page request); if checked out — creates Hold request

### Create Transaction — BORROWER role (POST)

```json
{
  "item": { "id": "<UUID>", "title": "<title>", "barcode": "<barcode>", "materialType": "book", "locationCode": "<shadow location code>", "lendingLibraryCode": "<shadow library code>" },
  "patron": { "id": "<existing user UUID>", "barcode": "<barcode>" },
  "pickup": { "servicePointId": "<SP UUID>", "servicePointName": "<name>", "libraryCode": "<code>" },
  "role": "BORROWER"
}
```
- Patron must already exist before this call
- `servicePointId` is required; name is optional
- Creates virtual item in mod-circulation-item
- Creates Hold request with status Open - Not yet filled
- `lendingLibraryCode` and `locationCode` are required; see Shadow Location note below

### Create Transaction — BORROWING-PICKUP role (POST)

```json
{
  "item": { "id": "<UUID>", "title": "<title>", "barcode": "<barcode>", "materialType": "book", "locationCode": "<shadow location code>", "lendingLibraryCode": "<shadow library code>" },
  "patron": { "id": "<existing user UUID>", "barcode": "<barcode>" },
  "pickup": { "servicePointId": "<SP UUID>" },
  "role": "BORROWING-PICKUP"
}
```
- Patron must already exist
- `lendingLibraryCode` and `locationCode` are required; see Shadow Location note below

### Create Transaction — PICKUP role (POST)

```json
{
  "item": { "id": "<UUID>", "title": "<title>", "barcode": "<barcode>", "materialType": "book", "locationCode": "<shadow location code>", "lendingLibraryCode": "<shadow library code>" },
  "patron": { "id": "<UUID>", "group": "staff", "barcode": "<barcode>", "localNames": ["<FirstName>", "<LastName>"] },
  "pickup": { "servicePointId": "<SP UUID>" },
  "role": "PICKUP"
}
```
- Patron does NOT need to exist beforehand (virtual patron created)
- Virtual item created in mod-circulation-item
- `lendingLibraryCode` and `locationCode` are required; see Shadow Location note below

### Shadow Location — `lendingLibraryCode` and `locationCode`

`lendingLibraryCode` is a required parameter and acts the same as `locationCode`. Both fields must be included in the payload for BORROWER, BORROWING-PICKUP, and PICKUP roles. These fields contain the shadow location code and shadow library code that exist in the **external lending library** but are **also created in the current library** with the flag `isShadow = true`. Shadow locations are not displayed in any FOLIO application UI — they are only used in **circulation rules**.

- If `lendingLibraryCode` and `locationCode` are provided and reference valid shadow locations → the virtual item's effective location is set to that shadow location → the mapped circulation rules apply (if any exist).
- If `lendingLibraryCode` and `locationCode` are not provided or contain non-existing shadow location codes → the effective location of the virtual item falls back to `DCB`.

These fields therefore define the **effective location of the virtual item** when it is created.

### Self-Borrowing (POST, BORROWING-PICKUP + selfBorrowing flag)

```json
{
  "item": { ... },
  "patron": { ... },
  "pickup": { "servicePointId": "<SP UUID>" },
  "role": "BORROWING-PICKUP",
  "selfBorrowing": true
}
```

### Update Transaction Status (PUT)

```
PUT /dcbService/transactions/{id}/status?apiKey=<key>
Body: { "status": "<NEW_STATUS>" }
```
- Not allowed for LENDER role via this endpoint
- Only allowed when current status is CREATED (for some role updates)

### Get Transaction Status (GET)

```
GET /dcbService/transactions/{id}/status?apiKey=<key>
Response: { "status": "<CURRENT_STATUS>" }
```

## Common Verification Patterns

### 1. Verify transaction creation state (Lending library)

```
Action:   POST transaction via API with role=LENDER, then check Requests app for item barcode
Expected: Request status = "Open - Not yet filled"
          Item status = "Paged"
          Pickup service point name contains "DCB_" prefix
          Request Action menu shows only "Cancel Request"
          Circulation log shows action "Created" for the item
```

### 2. Verify first check-in transition (Lending library)

```
Action:   In Check in app, scan item barcode used in transaction
Expected: Item is checked in
          Item status changes to "In transit"
          Transaction status changes to "OPEN"
          Circulation log: action "Checked in", item status description "In transit to <SP>"
```

### 3. Verify DCB virtual user creation

```
Action:   Search in Users app for user barcode/name used in Lender transaction
Expected: User is found
          User type = "dcb"
          Action menu on user details is disabled
          No actions available: create patron blocks, create fee/fine, create request, add note
```

### 4. Verify check-in at Pickup library triggers AWAITING_PICKUP

```
Action:   In Check in app (Pickup/Borrowing library), scan DCB virtual item barcode
Expected: Item status = "Awaiting pickup"
          Transaction status = "AWAITING_PICKUP"
          Note: status and item status only change if service points match between check-in and request creation
```

### 5. Verify loan creation on ITEM_CHECKED_OUT transition

```
Action:   PUT transaction status to ITEM_CHECKED_OUT (or manual checkout at Pickup library)
Expected: Loan is created for the patron in Users > Open Loans
          Hold request updated to "Closed - Filled"
          Item status = "Checked out"
          Circulation log shows "Checked out" action with Source = "System" (for automatic checkout)
          OR Source = actual staff user (for manual checkout)
```

## ECS / Multi-Tenant Notes

DCB transactions inherently span multiple tenants (each library is a separate FOLIO tenant in ECS). Test cases reference two-tenant setups:
- Lending library tenant (contains real item)
- Borrowing library tenant (contains real patron)
- Pickup library tenant (may be same as borrowing)

Key ECS-specific observations from test cases:
- E2E tests require access to two tenants simultaneously (different browser windows)
- DCB-created service points in the lending tenant follow the naming pattern `DCB_{libraryName}_{servicePointName}`
- OAI-PMH tests confirm DCB instances/holdings are NOT retrieved in OAI-PMH harvest responses
- Bulk edit: DCB type users are filtered out from Bulk edit operations
- Circulation log in Central tenant shows ECS loan renewal actions for DCB items (case 1259786)

## DCB Admin for Libraries (Separate Application)

DCB Admin for Libraries is a separate web app for library-level staff (not consortium admins). Key features:

### User Roles (Keycloak)
- `LIBRARY_ADMIN` — full access: view patron requests, supplier requests, place staff requests, view mappings/locations
- `LIBRARY_READ_ONLY` — requesting only; directed to "Requesting" section on login; "requesting-only mode" shown in header

### Key Sections
- **Requesting** — search and place requests; supports Staff requesting (on behalf of patron) and Walk-up requesting (visiting patron / direct on-site borrowing)
- **Patron Requests** — all requests placed by patrons from this library; filterable by status, date, supplying library, active workflow, etc.
- **Supplier Requests** — all requests for which this library is the supplier
- **Individual Patron Request** — tabs: General, Bib record, Supplying, Borrowing, Pickup, Audit log
- **Service** — LMS connection info
- **Mappings** — ItemType, patronType, Location reference value mappings (read-only by default)
- **Locations** — pickup locations list with availability status
- **Settings** — personal settings (dark mode)

### Request Actions (Individual Patron Request)
- `Check for Updates` — manually triggers DCB polling of involved library systems
- `Force Cleanup` — triggers manual cleanup: finalises request and attempts to delete virtual records

### Active Workflow Values
- `RET-PUA` — Pickup Anywhere (3 different libraries)
- `RET-STD` — Standard (supplier different from borrower/pickup)
- `RET-LOCAL` — Local (all 3 roles same library)
- `RET-EXP` — Expedited / On-site borrowing

### Search Options (Requesting section)
Title, Keyword, Author, ISSN, ISBN, Subject, Language, Publisher, Format, Cluster record ID; advanced search supports AND/OR/NOT operators

## Key Business Rules for Test Cases

1. Only `Cancel Request` action is available in the Action menu for DCB requests in all roles and at all transaction statuses. (cases)
2. DCB virtual users have User type = `dcb`; their Action menu is disabled in the Users app. (cases)
3. Fee/Fine actions (`New Fee/Fine`, `Fee/fine details`) are hidden in the Check in app for Lending library DCB transactions. (cases + KB)
4. Item links (title, barcode) are disabled in Borrowing and Pickup library flows in Loan details, Request details, and Circulation log. (cases + KB)
5. All loan actions are disabled for DCB loans when the loan is related to a virtual patron (User type = `dcb`). When the patron is a real user and the item is virtual (Borrowing and Pickup library roles), all loan actions remain available. (cases + KB)
6. DCB service points are automatically assigned to the common DCB Calendar. (cases)
7. DCB patron notifications (notices) are NOT sent to virtual patrons in Lending and Pickup libraries. (KB)
8. Fee/Fines are NOT applied to virtual patrons in Lending and Pickup libraries. (KB)
9. The pickup service point name follows the pattern `DCB_{libraryName}_{servicePointName}`. (cases + KB)
10. Transaction STATUS (via PUT `/transactions/{id}/status`) can be updated without role restrictions. The TRANSACTION itself (via PUT `/transactions/{id}`) can only be updated if the role is not LENDER and the current transaction status is CREATED. (cases)
11. When `localNames` are provided in the transaction payload, the DCB user is created with those First/Middle/Last names; without `localNames`, default lastName is `DcbSystem`. (KB, since Sunflower SP#3)
12. Circulation log entries for automatic (system-driven) DCB actions show `System` in Source and `DCB` in Service Point. There is no entity named "DCB SP" — the service point used in DCB actions is simply named `DCB`. (cases + KB)
13. Location-based circulation rules apply to DCB virtual items — the loan policy, overdue fine policy, and lost item fee policy are determined by the `locationCode` specified in the transaction. (cases)
14. DCB type users are excluded from Bulk Edit operations. (cases)
15. DCB instances and their holdings/items are excluded from OAI-PMH harvest responses. (cases)
16. Cancellation can be initiated by FOLIO staff (via Cancel Request) at any transaction status before CLOSED. (cases)
17. For BORROWING-PICKUP role: check-in only changes item status and transaction status if the check-in service point matches the service point from transaction creation. (KB)
18. When an item is not in Available status at transaction creation (Lender role), a Hold request is created instead of a Page request. (KB)
19. For external API calls to the renewal endpoint: renewing a DCB item via the external API is forbidden when the loan policy does not allow renewal, the transaction is not in ITEM_CHECKED_OUT status, or the role is not Lender. These restrictions apply specifically to the external API renewal call and do not restrict renewals initiated through other means. (cases)
20. Hold shelf expiration closes a DCB transaction automatically for all roles (Lender, Borrower, Borrowing-Pickup, Pickup). (cases)
