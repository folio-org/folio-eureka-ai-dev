## What is Check in

The Check in app (route `/checkin`) processes items returned to the library at a service point. It closes open loans, updates item statuses, triggers request fulfillment (hold shelf or delivery), routes items in transit to other service points, records in-house use, and handles associated fees/fines. Staff interact primarily by scanning or typing item barcodes; all follow-up decisions are surfaced through mandatory pop-up modals.

> **Identifier convention for this area:** the team writes circulation cases with **symbolic placeholders the executor fills at run time** — `service point S` / `S1`, `<barcode>`, `<title>`, `<material type>`, "item with at least one open request" — not invented concrete values. Do NOT fabricate a specific barcode (e.g. `12345`) or a named service point (e.g. `SP-A`); use `S`/`<barcode>` as the real cases do (see C7148). Concrete values only when the exact value is itself under test (a barcode with a trailing space, a specific fee amount).

## Core Check in Flow

1. Staff scans item barcode into the **"Scan or enter barcode to check-in item"** field [confirmed] and presses Enter
2. FOLIO checks item status and any open requests or loans
3. Appropriate pop-ups appear (if triggered) — each must be dismissed before the next
4. Staff dismisses pop-ups → item appears in **Scanned Items** table [confirmed]
5. Item status updates based on context (see Item Status Outcomes below)
6. Staff clicks **End session** [confirmed] when done → notices sent to patrons

---

## Item Status Outcomes After Check in

| Scenario | Resulting Item Status |
|---|---|
| No open requests, checked in at effective location service point | **Available** |
| No open requests, checked in at a different service point | **In transit** |
| Open page/hold request, checked in at pickup service point | **Awaiting pickup** |
| Open delivery request, staff clicks "Close and check out" | Checked out to patron |
| Open delivery request, staff clicks "Close" only | **Awaiting delivery** |
| Item part of floating collection, checked in at floating location | **Available** (effective location changes) |
| In-house use recorded | **Available** (status unchanged; usage stat recorded) |

## Pop-ups That Can Occur During Check in

Pop-ups are **mandatory** — there is no way to disable them. Each must be acknowledged before proceeding.

| Pop-up | When triggered |
|---|---|
| **Item status** | Item is in a status that requires staff attention (e.g. In transit, Awaiting pickup) |
| **Check in notes** | Item has check in notes attached to it |
| **Multiple and/or missing pieces** | Item record has a number of pieces > 1, or has a missing pieces note |
| **Awaiting pickup for a request** | Item is checked in at the patron's requested pickup service point |
| **In transit** | Item needs to be routed to another service point |
| **Route for delivery request** | Item has an open delivery request |

## Routing to Another Service Point (In Transit)

An item is routed In transit when:
- Checked in at a service point **not assigned** to its effective location
- Item has an open request with pickup at a **different** service point

### In transit flow
1. Scan barcode → **"In transit"** [confirmed] dialog appears
2. Dialog body: `"Route {title} ({materialType}) (Barcode: {barcode}) to {servicePoint}."` [confirmed]
3. **"Print slip"** checkbox present; default = **checked** [confirmed] (inherits service point setting per UICHKIN-53)
4. Click **"Close"** [confirmed] → browser print window opens with transit slip → item status → **In transit**
5. After closing print window: item row shows in Scanned Items with time, title (material type), barcode, effective call number string, location, status [confirmed]
6. **"Print transit slip"** appears in ellipsis menu for reprinting [confirmed]

## Floating Collections

A floating collection allows items to stay at whichever library service point they are returned to, instead of being routed back to their home location.

### Rules
- Both the item's current location AND the check-in location must be designated as **floating** in Settings → Tenant
- If both are floating: item's effective location **changes** to the check-in location; item becomes Available; no transit slip generated
- If only one is floating (or neither): normal routing applies
- Only one floating location per service point is recommended
- Floating must be enabled at installation level

## Hold Shelf Fulfillment (Request at Pickup Service Point)

When a requested item is checked in at the patron's chosen pickup service point:

1. Scan barcode → **Awaiting pickup for a request** dialog appears
2. Dialog shows: patron name, pickup service point
3. Optional: print hold slip (checkbox)
4. Click **Close** → item status → **Awaiting pickup**
5. FOLIO sets **hold shelf expiration date/time** automatically (based on service point settings)
6. Pickup notice sent to patron when the check in **session ends** (if notice policy configured)

**Important:** The pickup notice is NOT sent immediately on check in — it is sent when the session ends.

---

## Delivery Fulfillment (Delivery Request)

A delivery request is triggered when the item is checked in at **any** location (not just a specific service point).

### Two options at the "Route for delivery request" dialog:

**Option 1 — Check out immediately:**
- Click **Close and check out** → Check out window opens → item automatically checked out to patron

**Option 2 — Wait to process:**
- Click **Close** → item status → **Awaiting delivery**
- Staff processes delivery separately

---

## Backdating Check in

Used when the library was closed on the actual return date and fines should not accrue.

1. Click the **pencil icon** next to Date/Time Returned
2. Change date and/or time to the desired backdated date
3. Scan item as normal
4. Scanned Items table shows backdated time in Time returned column
5. Click **info icon** to see actual check in time alongside backdated time

**Effect:** Fees/fines calculated as if item was returned on the backdated date; overdue fines reduced or eliminated accordingly.

---

## In-House Use Recording

Used to record that an available item was used within the library without being checked out (e.g. reference items, items on display).

### Requirements
- Item must be **Available** (not on loan)
- Item must have **no open requests**
- Must be checked in at a service point **assigned to the item's effective location**

### How it works
- Scan barcode → house icon appears in In-house use column
- Item status remains **Available**
- Usage statistic is recorded for reporting purposes

---

## Fees/Fines at Check in

### Automatic fees/fines
- If the item is overdue, overdue fines are calculated automatically on check in
- Fine amount shown in **Time returned** column
- Staff can click **… > Fee/fine details** to view, pay, waive, or cancel the fine

### Manual fee/fine creation
Staff can create a new fee/fine directly from Check in:
1. `… > New Fee/Fine`
2. Select Fee/fine owner (required)
3. Select Fee/fine type (required)
4. Enter amount
5. Optional: add staff note, toggle patron notification
6. Click **Charge only**

---

## Session Management

### Ending a session
- Click **End session** → clears Scanned Items table → patron notices sent
- **Pickup notices** for hold requests are sent at session end (not during check in)

### Auto-end session
- Default: session ends automatically after **3 minutes of inactivity**
- Configurable in Settings → Circulation → Auto-end session
- Can be disabled entirely

### Effect of session end
- Scanned Items table cleared
- All pending notices dispatched to patrons

## Staff Slips

Staff slips are printed documents generated during check in. Configured in Settings → Circulation → Staff slips.

| Slip | When printed |
|---|---|
| **Transit slip** | Item goes In transit |
| **Hold slip** | Item checked in at pickup service point (hold shelf fulfillment) |
| **Request delivery slip** | Item has a delivery request |

Each slip has a print checkbox at the pop-up dialog. Staff can opt out per item.

---

## Loan Anonymization

Libraries can configure FOLIO to anonymize loans after check in (removes link between loan record and patron):
- Configured in Settings → Circulation → Loan anonymization
- Option: *Anonymize closed loans immediately after loan closes* — anonymization occurs after the session ends
- Scheduled process run by system administrator

## Common Verification Patterns (from TestRail cases)

### Pattern 1 — Backdate check in and verify loan record
1. Note item's open loan due date/time
2. Open Check In at the loan's service point
3. Edit **Date returned** and **Time returned** → choose date/time before due date
4. Scan item barcode
5. **EXPECT:** Scanned Items table shows backdated Time returned value
6. Actions → **Loan details** → open loan actions record
7. **EXPECT:** "Return date/time" matches the backdated values entered at step 3

**Variation — item record circulation history:**
After backdating, navigate to item in Inventory → **Circulation history** accordion
- **EXPECT:** "Check in date" = system date/time (NOT the backdated time); Service point = current service point; Source = staff user name

### Pattern 2 — In transit modal sequence
1. Set user service point to S (where S is not assigned to item's effective location)
2. Scan item barcode
3. **EXPECT:** Modal heading "In transit"; body `"Route {title} ({materialType}) (Barcode: {barcode}) to {servicePoint}."` [confirmed]; "Print slip" checkbox **checked** by default
4. Close modal
5. **EXPECT:** Browser print window with transit slip appears
6. Close print window
7. **EXPECT:** Item row in Scanned Items shows time, title (material type), barcode, effective call number string, effective location, status = **"In transit"**
8. Open ellipsis menu
9. **EXPECT:** **"Print transit slip"** link available [confirmed]

### Pattern 3 — Multipiece item confirmation
**Item with pieces count > 1 (no missing pieces):**
1. Scan item barcode
2. **EXPECT:** Modal heading "Confirm multipiece check in" [confirmed]; body shows title, barcode; "Number of pieces" label with value below it; "Description of pieces" if present
3. Click **Cancel** → **EXPECT:** Item is NOT checked in; does not appear in list
4. Scan item again → click **Check in** → **EXPECT:** Item IS checked in

**Item with missing pieces noted:**
1. Scan item barcode
2. **EXPECT:** Same modal plus "Number of missing pieces" and "Description of missing pieces" sections
3. Click **Check in** → **EXPECT:** Item checked in

**Item with pieces = 1, no descriptions, no missing pieces:**
- **EXPECT:** Modal does NOT appear; item checked in directly

### Pattern 4 — Check in notes modal
1. Scan item with 2+ check in notes
2. **EXPECT:** "Confirm check in" modal appears [confirmed]; notes sorted most recently added at top; each note shows: date/time added, note text, user name (format: Lastname, Firstname)
3. Click **Cancel** → **EXPECT:** Modal closes; item NOT checked in
4. Scan again → click **Confirm** → **EXPECT:** Modal closes; item IS checked in
5. In Scanned Items, click ellipsis → **"Check in notes"** [confirmed] → modal opens again showing same notes → Click **Close** → modal closes

### Pattern 5 — Claimed returned resolution
1. Scan item with status **Claimed returned**
2. **EXPECT:** Modal heading "Check in claimed returned item" [confirmed]; body `"{title} ({materialType}) (Barcode: {barcode}) has been claimed returned."` [confirmed]; 3 buttons: **Cancel**, **Found by library**, **Returned by patron** [confirmed]
3. Click **Cancel** → item NOT checked in
4. Re-scan → click **Found by library** → item checked in
5. Navigate to loan details → top action row:
   - Action: `"Checked in (found by library)"`
   - Action date: date/time of check in; Item status: resulting status
6. Separately: scan another claimed returned item → click **Returned by patron** → loan action = `"Checked in (returned by patron)"`

### Pattern 6 — Multiple modals ordering (item with all conditions)
When an item has: **Missing status + multipiece/missing pieces + check in note + in transit**:
1. Scan → **item status** modal appears first (Missing confirm)
2. Cancel at any modal → item NOT checked in; NO further modals appear
3. If confirmed at step 1 → **Multipiece/missing pieces** modal appears second
4. If confirmed → **Check in notes** modal appears third
5. If confirmed → **In transit** modal appears last (if routing applies)

### Pattern 7 — Wildcard barcode lookup ("Select item" modal)
*(Requires "Perform wildcard lookup" setting enabled)*
1. Enter partial barcode pattern
2. **EXPECT:** "Select item" modal opens [confirmed]; header `"List of items: choose one {count} Records found"` [from source]
3. **Pagination:** When > 100 results: "Previous" button disabled; counter `"1-100"` shown; "Next" button enabled
4. Click **Next** → counter changes to `"101-200"`; "Previous" enabled
5. Click **Previous** → back to `"1-100"`; "Previous" disabled
6. When absent call number: `"-"` displayed in Call number column [confirmed]
7. Select item → item shown in Scanned Items; `"-"` in Effective call number string and In-house use columns when values absent [confirmed]

### Pattern 8 — Fee/fine at check in with "/" in barcode
1. Scan item whose barcode contains `"/"` character
2. Item is scanned/checked in successfully
3. Click `"..."` → select **"New Fee/Fine"** [confirmed]
4. **EXPECT:** **"New fee/fine"** modal opens [confirmed]
5. Fill mandatory fields → click **"Charge only"** → fee/fine created; `"(fees/fines owed)"` [confirmed] text appears in Time returned column
6. Click `"..."` → **"Fee/fine details"** [confirmed] → page opens with created fee/fine

### Pattern 9 — Service point switching and circulation log
1. Check in item at service point SP1
2. Switch service point (user icon → "Switch service point" → select SP2)
3. Check in second item at SP2
4. Open Circulation log → search by Item 1's barcode
5. **EXPECT:** Service point column shows SP1 for Item 1
6. Search by Item 2's barcode → **EXPECT:** SP2 shown for Item 2

### Pattern 10 — Fee/fine items in same session
1. Check in item WITH fee/fine owed
2. **EXPECT:** `"(fees/fines owed)"` label in Time returned column; status changes to Available/In transit
3. Check in item WITHOUT fee/fine owed

## Business Rules

### Positive Rules (user CAN do)
- User can check in items and see time returned, title (material type), barcode, effective call number string, effective location, and status in Scanned Items table [confirmed — multiple cases]
- User can backdate check in by editing Date returned and Time returned fields [confirmed — case 587]
- User can view loan details, item details, and patron details via Actions menu (with appropriate additional permissions) [confirmed — case 588]
- User can print transit slip immediately at check in or reprint later via Actions menu [confirmed — case 588]
- User can print hold slip at check in when item is at patron's pickup service point [confirmed — case 7148]
- User can view request details from Actions menu when item has a request [confirmed — case 7148]
- User can confirm or cancel check in for items in special statuses (Missing, Declared lost, Withdrawn, Lost and paid, Claimed returned) [confirmed — cases 9194, 10974]
- User can check in items with "/" characters in barcodes and apply fee/fines afterwards [confirmed — case 552474]
- User can check in items with spaces in barcodes; spaces are preserved [confirmed — case 566154, UICHKIN-424 fix]
- User can use wildcard barcode lookup to select from multiple matching items (when setting enabled) [confirmed — cases 651544, 688737]
- SessionId persists across app navigation within one session; switching to Check Out and back does not create a new session [confirmed — case 398022]
- User can check in items from data tenant via Central tenant (ECS) [confirmed — case 692117]
- User can check in items with and without fee/fines within the same session; Time returned column label reflects presence/absence of fee/fine per row [confirmed — case 1263908]
- User can check in items after service point switch; circulation log reflects correct service point per item [confirmed — case 425]

### Negative / Edge-Case Rules (must NOT happen or requires caution)
- Cancelling any mandatory modal at any step in the modal sequence results in item NOT checked in and NO further modals appearing [confirmed — case 7149]
- Cancelling at multipiece modal does NOT clear the session's check-in history — existing items in list remain [fixed in UICHKIN-88]
- Backdating a check in does NOT change the "Check in date" shown in the item's circulation history in Inventory — that always shows the system date [confirmed — case 9179]
- Item barcode must NOT be trimmed before being sent to the backend; spaces at start or end are intentional and distinct barcodes [confirmed — case 566154, UICHKIN-424]
- "Time returned" must NOT show the backdated time as the system time — the column shows the backdated time but the actual system time is accessible via info icon [confirmed — case 411866]
- No JavaScript errors should appear after a user logs out while the Check in app is open, even after 20 minutes of inactivity on the login page [confirmed — case 418579]
- Virtual/DCB patron items must NOT show "Item details", "New Fee/Fine", or "Fee/fine details" in the Actions menu [from UICHKIN-398, UICHKIN-403]

### Modal Ordering Rule (critical for test design)
When multiple modal conditions apply to a single item, modals appear in this fixed order:
1. Item status (Missing, Declared lost, Withdrawn, Lost and paid, Claimed returned) — **first**
2. Multipiece / missing pieces — **second**
3. Check in notes — **third**
4. In transit / Hold / Delivery routing — **last**

Cancelling at any modal stops the entire check in; no subsequent modals appear.

### Barcode Handling Rules
- **Wildcard lookup:** Only activated when "Perform wildcard lookup of items by barcode in circulation apps (Check in, Check out)" is enabled in Settings → Circulation → Other settings
- **Spaces preserved:** Barcodes with leading/trailing spaces are treated as distinct barcodes (not trimmed) — since UICHKIN-424 (Ramsons)
- **Special characters:** Barcodes with `"/"` are handled correctly

## Authoring style (measured 2026-07-23)

Check-in cases split ~50/50 `Functional` / `Other` (pick per scenario), median ~6 steps. **Check-in is the one area where the team regularly sets `User Journey = Yes` (~18% of cases)** — and it does so for a specific shape: a single case that **walks every branch/outcome a condition can produce** instead of one case per branch. Reproduce this when a check-in scenario has multiple end states:
- **Special item statuses through the confirm modal** (C9194, Journey): one case enters an item of each status (`Declared lost`, `Withdrawn`, `Lost and paid`, ± suppressed-from-discovery) and clicks **both** Cancel (item NOT checked in) and Confirm (item checked in, status transitions) for each — all statuses × both branches in one case, using the exact `Check in {status} item?` modals.
- **Item with an open request** (C7148, Journey): check in at a non-pickup service point (→ In transit + transit slip + reprint), then switch to the pickup service point and check in again (→ Awaiting pickup + hold slip + reprint) — both fulfillment outcomes in one case.
- **Multipiece / multiple stacked modals** (C590, C7149, Journey): walk the full fixed modal order (item status → multipiece → check-in notes → routing) in one case rather than splitting per modal.

So for check-in, prefer a `User Journey = Yes` case bundling all branches when a condition is multi-outcome; keep single-outcome checks (backdate, "Time returned" display, session stability) as compact atomic `Other`/`Functional` cases.

## Key Business Rules for Test Cases

1. **Item checked in at its effective location service point → Available** (if no open requests)
2. **Item checked in at a different service point → In transit** — "In transit" dialog appears; destination shown; transit slip printed by default
3. **Hold request at pickup service point → Awaiting pickup** — "Awaiting pickup for a request" dialog; hold shelf expiration date set automatically
4. **Delivery request triggers at any service point** — not tied to a specific pickup location; two resolution options: "Close and check out" (immediate) or "Close" (→ Awaiting delivery)
5. **Pop-ups are mandatory** — cannot be disabled; Check in notes, missing pieces, item status modals must all be dismissed; cancelling any = item NOT checked in
6. **Modal order is fixed:** item status → multipiece → check in notes → routing
7. **Pickup notice sent at session end, not at check in** — notices batch until End session is clicked
8. **In-house use requires Available item + no requests + same service point** — item status stays Available; in-house use statistic recorded
9. **Floating collection changes effective location** — both locations must be designated floating; item stays at check-in location without transit slip
10. **Backdating affects fee/fine calculation but NOT circulation history** — overdue fines recalculated; item record "Check in date" always = system date
11. **Auto-end session after 3 minutes inactivity by default** — configurable in Settings → Circulation → Auto-end session
12. **Check in capability does not include patron/item detail viewing** — requires separate Users and Inventory capabilities
13. **New Fee/Fine from Check in requires Fee/fine owner and type** — both required fields
14. **Transit slip can be reprinted after the fact** — via … > Print transit slip in Actions menu
15. **Check in notes cannot be skipped** — notes reviewed at check in; dismissible via Actions → Check in notes after
16. **Anonymization runs after session ends** — not immediately at check in
17. **Multiple pieces pop-up always appears** — when pieces count > 1 OR missing pieces note present
18. **SessionId is stable within a session** — navigating away and back does not reset the session ID (since Poppy)
19. **X button is absent on item-status-confirmation modals** (`Check in missing item?`, and equivalents for Withdrawn/Declared lost/Lost and paid) — only `Cancel`/`Confirm` are offered there, with default keyboard focus on `Confirm`. Regular confirmation modals (`Confirm multipiece check in`, `Confirm check in` with notes) DO have the X button (focus not on it, on the primary action instead). Don't assume every check-in modal has the same button layout — assert per modal type. (cases — C1405049, mirrors the equivalent Check-out pattern, jira: UICHKIN-510)
19. **Barcode spaces preserved** — leading/trailing spaces in barcodes are intentional; not trimmed (since Ramsons)
20. **Virtual/DCB items hide fee/fine and item details actions** — since Quesnelia
