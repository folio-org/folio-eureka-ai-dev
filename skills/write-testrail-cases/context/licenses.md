## What is Licenses

The Licenses app manages legal contracts and terms of use for licensed content in FOLIO ERM. It tracks license metadata, term conditions, organizations, internal contacts, and attached documents. Licenses can have amendment sub-records to capture changes over time and are visible from linked agreements.

## Key Terms

| Term | Definition |
|---|---|
| License | Contract and terms-of-use record governing access and permitted actions |
| Amendment | Child record representing a modification to a parent license |
| Term | Structured license condition (text, integer, or pick-list value) |
| Core document | Primary legal file/link/location attached to a license |
| Supplementary document | Additional supporting document with category |
| Agreement link | Relationship from Agreements app to one or more licenses |

## Record Hierarchy / Architecture

Licenses
  - License record
    - License information
    - Internal contacts (linked Users)
    - Organizations (linked Organizations)
    - Core documents
    - Terms (primary and optional)
    - Supplementary documents
    - Amendments
      - Amendment terms / documents / contacts / organizations

### License Term "Name" field validation (confirmed both in UI and API — C1385636, C1347204)
- Must **start with a letter** and contain **only letters, digits, or underscores** thereafter (no spaces, punctuation, or symbols of any kind — this includes trailing spaces, which also fail).
- UI validation on blank/invalid Name: field highlighted red, error `Please fill this in to continue` (same generic message for empty, leading-underscore, or symbol-containing input — the UI does not differentiate *why* the name is invalid).
- API validation (`POST`/`PUT /licenses/custprops`) returns the **specific** message: `Custom property name must start with a letter and contain only letters, digits or underscores` — use this exact string in API-level test case expected results (distinct from the UI's generic message).
- Non-Latin/Unicode letters ARE valid as long as the very first character is a letter and the rest are letters/digits/underscores — e.g. `Property_汉` and `test李` both succeed. Don't assume the rule is "ASCII only"; it's "letter-first, then \[letters incl. Unicode, digits, underscore\]".
- The (i) info icon next to "Name" in both the New term modal and the Edit (Supplementary properties) modal shows the same tooltip text: `A term 'name' is used when outputting the supplementary property data in a machine readable format intended to be used by external systems or programs that access the term data. It is not intended to be displayed to users (staff or patrons). It should be a short string which must start with a letter, and can only contain letters, numbers, and underscores. Changes to the term name will affect any external systems using license term data and changes should not be made without consulting those responsible for relevant external systems and software.`

## Document Filter Builder (Search & filter — "Core documents" / "Supplementary documents" facets)

> Confirmed via C422210 (Filter amendments by core documents); same builder pattern applies to License search's "Core documents"/"Supplementary documents" filters (C422201, C422203).

- Trigger: expand the "Core documents" (or "Supplementary documents") filter accordion → click `Edit document filters` button → opens a popover titled with a `Document filter 1` card.
- Each filter card has three controls plus an `Add rule` button: **Attribute** dropdown (`Name`, `Note`, `Physical location`, `URL`, `Content type`, `File name`), **Operator** dropdown (`Is`, `Contains`, `Does not contain`), and a free-text **Value** box.
- `Save & close` stays disabled until at least one complete rule (Attribute + Operator + Value) is entered.
- **Rules within the same card are combined with AND** (adding a rule via "Add rule" prepends the label "AND" to the new row) — a record must match every rule in that card.
- **Multiple filter cards (added via "Add filter", e.g. "Document filter 2") are combined with OR** — a record matching any one full card's AND-conditions is included in the result.
- Each card has its own trashcan icon to delete it. Filter state (all cards/rules) persists when reopening "Edit document filters" — it is not reset on popover close.
- Test both directions of "Contains" vs "Does not contain" and confirm "Is" requires an exact match — these produce materially different result sets, not just cosmetic wording differences.

## Sort Options — License Search Results (confirmed, C343046)

- Default: sorted by **Name ascending** (up-chevron next to "Name" column) — note the default result set is also filtered to `Active` status only until that filter is cleared.
- Sortable columns: `Name`, `Status`, `Start date`, `End date`, `Type` — clicking toggles ascending (up-chevron) / descending (down-chevron).
- **Open-ended licenses / licenses without an End date are grouped together, not interleaved by date, when sorting on "End date"**: they sit at the **bottom** of the list in ascending order and at the **top** in descending order, and are not sorted amongst themselves. Always include at least one open-ended/no-end-date license in an End-date sort test to catch regressions in this grouping behavior.

When S3 is selected, additional fields are required: `S3 access key`, `S3 bucket name`, `S3 bucket region`, `S3 endpoint`, `S3 object prefix`, `S3 secret key` (key/secret can alternatively come from an IAM role or env var depending on environment setup). ## Acquisition Units

- Acquisition units accordion appears on the license Edit form; each assigned unit has a trashcan icon with tooltip `Remove {acquisition unit name}`. Removing the **last** acquisition unit makes the "Acquisition units" accordion disappear from the license **view** entirely (not shown empty) after save. (cases — C1028998)
- **A user assigned to multiple acquisition units gets the union of each unit's permissions on records restricted to any of those units** — e.g. assigned to Unit A (Create/Edit/Delete restricted) and Unit B (Create/Delete restricted only), the user has full Edit/Duplicate/Delete access, including on child Amendments, to a license assigned to both units simultaneously. Don't assume multi-unit assignment is more restrictive — verify it against the specific permission each unit restricts. (cases — C1029002)

## Pick Lists (confirmed C464319, C464320, C464329)

A **pick list** is a tenant-defined enumeration backing a specific dropdown field elsewhere in Licenses — managed at `Settings > Licenses > Pick lists`, separate from Term Types/Term Names.

- The Pick lists Settings page shows a searchable table (columns `Category`, `# of values`) of every pick list; each row's `Category` name follows an `{Entity}.{FieldName}` convention (e.g. `License.Type`, `LicenseOrg.Role`) that identifies exactly which dropdown it drives.
- `New` on the main Pick lists pane adds an editable `Category` row; saving it re-sorts the table alphabetically, shows `# of values = 0`, and opens a 4th pane for that new category. A trashcan icon per row opens a `Delete pick list category` confirmation (Delete/Cancel).
- Selecting a category opens a 4th pane listing its `Pick list values` with its own `New` button — clicking it adds an editable `Label` field with `Save`/`Cancel`. A newly-saved value is **immediately selectable** in the corresponding dropdown on the License (or License Organization) form — e.g. a new `LicenseOrg.Role` value shows up right away in the `Role` dropdown when linking an organization to a license.
- Values can also be renamed and removed after creation (same edit-in-place pattern as adding).
- This is a genuinely separate mechanic from `Term Types`/`Term Names` (which validate license Term fields) — don't conflate the two when a scenario mentions "picklist" vs. "term type."

## Performance / Pagination Notes

- **Linked Agreements accordion paginates at 100 records per request** — for a license with >100 linked agreements, opening "Agreements linked to this license" issues multiple `/linkedAgreements` requests in batches of 100 (e.g. 201 agreements → 3 requests: 1-100, 101-200, 201-201), not one request per agreement and not a single unbounded request. Verify via the Network tab request count, not just that all agreements eventually render. (cases — C389580)

## Key Business Rules for Test Cases

1. The minimal fields to save a license are `Name`, `Type`, and `Status` (Name required; Type and Status are the other fields populated in the "create minimal license" flow). (cases — C762, C10993)
1a. `Record created` and `Record last updated` metadata: on creation both timestamps are equal; after an edit, `Record last updated` changes while `Record created` stays fixed (a common assertion in create/edit cases). (cases — C762, C1330)
2. Open ended and End date are mutually exclusive in license and amendment forms. (cases + github)
3. Internal contacts must be linked to Users app records; free-text contacts are not valid. (cases + github)
4. Organizations must be linked to Organizations app records; one organization can be primary. (cases + github)
5. Core document requires Name plus at least one of file, physical location, or URL. (cases + github)
6. Supplementary document requires Name, Category, and at least one of file, physical location, or URL. (cases + github)
7. Primary terms are always present; optional terms must be explicitly added per license. (cases + github)
8. File download permission is separate from general edit permission. (cases)
9. Amendments are child records that can be created, edited, deleted, duplicated, and searched independently. (cases + github)
10. Amendment terms supplement parent terms; conflicts require manual reconciliation. (github)
11. Duplicate license creates a reusable copy including terms, documents, contacts, and organizations. (cases + github)
12. Alternative names are searchable and can be used to find license records. (cases + github)
13. **Pick lists back specific dropdown fields (`{Entity}.{FieldName}` naming, e.g. `License.Type`, `LicenseOrg.Role`) and are managed at Settings > Licenses > Pick lists** — a newly-added value is immediately selectable in its corresponding form dropdown; this is a distinct mechanic from Term Types/Term Names. (cases — C464319, C464320, C464329)

## Authoring style (measured 2026-07-23)

License is the project's **most `Other`-pure area (~98%)**, median ~7 steps, `User Journey` ~3%. Nearly every case is record-CRUD / accordion management on the License record (terms, amendments, organizations, core/supplementary documents, internal contacts, linked agreements) or a Settings pick-list / storage-engine config — all `Other`. Reserve `Functional` only for genuine computed/contract behavior (custprops API validation). Preconditions carry the ERM setup (an existing License with the relevant accordion populated, a configured pick list / storage engine / acquisition unit). Keep single-accordion edits compact; document-storage and migration cases run longer only because of the Settings setup.
